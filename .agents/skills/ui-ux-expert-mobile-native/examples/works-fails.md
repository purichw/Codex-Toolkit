# Works / fails: native repair hypotheses

These are authored comparison briefs, **not rendered or human-validated native exemplars**. Use the
same content/state on both sides when producing comparison images. Never present this text as proof
that a particular layout is beautiful. Each pair contains a cause, not a stylistic blacklist.

## 1. Dense mobile list: comparison beats decoration

**Fails:** every row contains a large avatar, three filled actions, a brightly colored status and a
large amount. Names and amounts wrap, although the task is to compare amounts.
**Candidate that works for this task:** give amount/status stable roles, keep the frequent row action,
move less frequent actions into a discoverable menu, reduce decorative footprint and keep adequate hit
areas. Long names can wrap without pushing amounts into inconsistent columns.
**Why/check:** task hierarchy and geometry changed, not merely color. Compare longest row, negative/
unknown amount, selected state and open menu; no permission or action may disappear.
**Counterexample:** a dispatch flow needing frequent per-row confirmation may require its action inline.

## 2. Thai mobile form: grouping and keyboard, not prettier boxes

**Fails:** label/helper/value all centered, fixed-height fields clip Thai marks, and a bottom save button
is hidden when the address keyboard appears.
**Candidate:** center above-field names and app-owned select/date values as requested, keep prose/free
text leading, let content drive height, establish clear group gaps and a single inset/scroll owner.
**Why/check:** label-value association, script legibility and reachability improve together. Use long
name/error, open keyboard, focus last field, large native text setting and successful save/reopen.
**Counterexample:** do not convert a simple platform inline settings row into an elaborate form unasked.

## 3. Editorial app: a screen sequence, not a dashboard

**Fails:** article is split into equal rounded cards with repeated labels; the hero crop removes the
subject; an oversized title hides the opening information at large text.
**Candidate:** create headline/standfirst/body/caption roles, a useful readable measure for the window,
approved focal crop, and deliberate transitions through the article. Preserve useful native navigation.
**Why/check:** reading order and image meaning survive. Review first viewport, middle/end and captions,
not only the hero. Test larger text without losing the story or hiding a navigation control.
**Counterexample:** a digest designed for skimming may legitimately use cards and equal previews.

## 4. Branded native screen: not system-default versus beautiful

**Fails:** an approved expressive reference becomes a neutral template after applying platform defaults,
or an illustrated background makes form values unreadable.
**Candidate:** retain the reference's meaningful imagery, palette relationships and hierarchy; give
critical content a readable surface and familiar native behavior.
**Why/check:** platform behavior and brand character are different design layers. Compare asset crop,
text planes, control states and transitions. A gradient is not a failure by itself.
**Counterexample:** a quiet account settings screen need not imitate the promotional opening artwork.

## 5. Sheets and Back: looking native is not behaving natively

**Fails:** short-window form in a half-height sheet scrolls inside another scroll view; a custom close
throws away the draft; Android Back and iOS swipe-dismiss disagree with the visible actions.
**Candidate:** choose a suitable sheet/full-screen structure and one state owner, preserve or explicitly
confirm unsaved work according to the contract, and use platform-supported navigation integration.
**Why/check:** control/data ownership fixes the underlying issue. Test actual keyboard, completed and
canceled dismiss/back gestures, and return to the draft; a screenshot alone cannot prove this pair.
**Counterexample:** a quick choice list may work well in a compact sheet and need no full-screen editor.

## 6. Tablet/foldable: use space without spreading everything

**Fails:** phone card list stretches across the screen; a resize loses the selected item and opens a
new route. Headline measure and action distance become uncomfortable.
**Candidate:** choose a constrained column or list/detail when appropriate, share selection state,
and adapt by available window space while keeping the same task possible.
**Why/check:** geometry and task continuity improve. Inspect narrow/wide windows and transition between
them with a selection/draft active.
**Counterexample:** reading may need one centered column rather than an obligatory two-pane layout.

## 7. Micro-edit: restraint is a measurable outcome

**Fails:** correcting one icon also changes font, navigation bar and spacing on unrelated screens.
**Candidate:** verify the parent geometry and icon metrics, fix the actual shared/local owner, inspect
the affected control and one real neighbor, leave the rest intact.
**Why/check:** fewer unsolicited changes, same behavior and clearer alignment. Compare diff and renders.
**Counterexample:** a proven shared defect can justify a wider fix, with affected consumers checked.

## 8. Game-adjacent app UI: animate the character, not the tap targets

**Fails:** code substitutes approved art with emoji, avatar bounce shifts the name field, score/timer
cover the play area, and background/resume advances the timer incorrectly.
**Candidate:** preserve actual atlas/manifest and a stable layout box, separate visual motion from hit
regions, place overlays according to gameplay/hand occlusion, and implement agreed pause behavior.
**Why/check:** art identity, usability and lifecycle agree. Render key frames and record play/pause/resume.
**Counterexample:** deliberate moving targets in the actual game need game-specific hit testing; form
buttons outside the game must not inherit that behavior.
